# Persistence

Lessons are stored as plain files on disk — no database. Layout and paths are defined in `src/bun/paths.ts`; the store is `src/bun/store.ts` and the notes document is `src/bun/notes.ts`.

- **One folder per lesson** under the OS app-data dir: `~/Library/Application Support/tuto/lessons/<id>/` (`.tuto/` on non-mac). The id is `<date>-<topic-slug>-<random>`.
- **`lesson.json`** — the display snapshot the WebView sends each turn (feed, outline, current concept, exercises and their answered state, sticky notes) merged with bun-owned metadata (Claude session id, the lesson's `config`, timestamps). The WebView owns display state; the Bun process owns all file I/O. `saveLesson` spreads the snapshot, so a new display field reaches disk by being added to `LessonSnapshot` — and has to be optional, since records written before it exists will not carry it.
- **A saved feed item carries the whole card**, so a new card field reaches disk by existing. The exception is state the *learner* put there rather than the tutor: `selectedOption` on an answered question, and `taskStatus` on a lab lesson's step (`open` | `done` | `verified` | `failed`) with the `check` that produced it, which is what stops a resumed lab presenting ten finished steps as open ones and losing the output that explains the failed one. `checksAllowed` sits on the snapshot rather than on an item, because consent is given once for the whole lesson. The app's two kinds of feed entry split on exactly this: a **notification** (one line — a practice item added, a lab folder made) happened once and is saved, while the **machine notice** is deliberately *not*, because it describes a machine that may have changed and is re-derived from a fresh probe on resume (see `lab-mode.md`).
- **Sticky notes and question threads are saved by position, not by id.** Each names the card's index among the feed's cards and the section's index within it (`SavedSticky`, `SavedThread`); the WebView's item ids are counters handed out on load and mean nothing on disk. See `reading.md` and `questions.md`. A thread persists only what was said — in-flight and failed state is not written — and one with nothing in it is dropped, like an empty note.
- **A lab lesson's record also carries its last probe** — what this machine looked like while the lesson was open — so the next resume can say what has moved. Bun-owned metadata: the shape is `MachineProbe` in `src/bun/env-probe.ts` and the webview never looks inside it.
- **`config` is how the lesson was started** — its mode, for a codebase lesson the project it reads (see `lesson-modes.md`), and for a lesson taken as groundwork the `goal` it leads back to (see `prerequisites.md`). Because the goal lives here rather than in the tutor's head, a resumed detour still offers the way back. A lab lesson's `config` also carries `labDir` once its plan asked for a folder — the one field that is written mid-lesson rather than at the start. Records written before modes existed have no `config` and a top-level `language`; `store.configOf` reads those as topic lessons, so old lessons resume unchanged. Metadata merges over what is already on disk, so a save for a lesson that is no longer the open one cannot blank out its session id.
- **`notes.md` / `notes.json`** — the rendered notes document and its section tree. **Not written today**: the notes feature is switched off at `NOTES_ENABLED` in `src/bun/lesson-modes.ts`, so no card carries the routing field that would file into it. Lessons taken before it was switched off keep the files they already have.
- **Ownership split.** `saveLesson` writes after each turn/answer; `listLessons` powers the home screen; `resumeLesson` restores the session id and notes tree, then the WebView rehydrates from the record.
